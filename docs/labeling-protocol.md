# 标注集与准确率口径

这个文档回答两件事：**标签从哪来**，以及**为什么这里算出来的数不能叫「准确率」**。

## 一、标签怎么来的

用的是 `trace-label-v2`：标签取自**执行时的注入状态**，不是人读完轨迹后的主观判断。

| 标签 | 定义 | 怎么得到 |
|---|---|---|
| `clean` | 没注入任何故障，且执行成功 | 跑 `fault_type="none"`、记录 success |
| `recovered` | 注入了故障，恢复后最终成功 | 注入故障 + D 模式，看最终 success |
| `failed` | 注入了故障，最终没救回来 | 注入故障，最终 success=0 |
| `unjudgeable` | 输入不足（没有 error 级规则可跑） | 由覆盖率计算自动判定 |

生成脚本：`scripts/build_labeled_set.py`（49 条：24 clean / 17 failed / 8 recovered，backend=mock）。
产物：`tests/fixtures/labeled/{labels.json,traces/*.json}`，轨迹是 OTLP 格式，
所以检查器走的代码路径与检查别人时**完全一样**。

## 二、两个口径，必须分开报

| 口径 | 含义 | 用途 |
|---|---|---|
| **确诊（error 级）** | 至少一条 error 级发现 | 可以据此判失败 / 阻断 |
| **提示（warn 级及以上）** | 出现 warn 或 error | 提示到了，需要人看一眼 |

只报一档会误导：`hallucinated_number` 这类规则按设计就是 warn，
用 error 口径算召回会把它们全算成漏报；反过来只看 warn 又会把噪音当检出。

## 三、当前数字（49 条构造集，mock 后端）

| 口径 | 检出 | recall | 误报 | precision |
|---|---|---|---|---|
| 确诊（error 级） | 7/17 | 0.412 | 0 / 32 | 1.000 |
| 提示（warn 及以上） | 7/17 | 0.412 | 2 / 32 | 0.778 |

- `recovered` 单独一档：8 条里有 2 条被 `cycle_detected` 误报（恢复重放被当成循环），
  这是已知误伤，记在这里不藏。
- 分母为 0 时比率给 `None` 不给 0：0 和「没算」是两件事。

## 四、为什么 recall 只有 41%

漏掉的 10 条全是同一类故障：**内部自洽但结论错**。

| 故障 | 为什么规则抓不到 |
|---|---|
| `silent_corruption`（A 模式） | 工具返回被改了值，答案与工具一致 —— 没有任何可交叉验证的证据 |
| `stale_data` | 工具返回的就是旧版文档，答案忠实于它；「这是旧版」这件事轨迹里没有 |
| `incorrect_planning` | 步骤齐全、顺序错；只有靠通用动作词才判得出，纯执行型流程没有这个词 |

这三类需要**外部真值**（政策库、版本元数据、流程定义），不是靠轨迹内部一致性推得出来的。
检查器不是在这一点上「调得不够好」，是它拿不到判据。

## 五、不能怎么用

- ❌ 不能写成「准确率 41%」——样本是构造的，分布不是真实业务。
- ❌ 不能写成「误报率 0」——32 条里只有 2 条 recovered 有告警，样本太小，置信区间极宽。
- ✅ 可以写成「在 49 条构造集上，error 级 recall 0.41 / precision 1.00，warn 级误报 2/32」。
- ✅ 可以当**回归护栏**：改规则后重跑 `python scripts/eval_labeled.py`，看两组数有没有退化。

## 六、要变成真准确率还差什么

1. **外部真实轨迹**（至少 30 条，正常 / 已恢复 / 未恢复三档都有），现在只有本仓库自己跑出来的。
2. **独立标注**：标注者不能是规则作者，且只看任务约束与轨迹、不看规则实现。
3. **分歧处理**：两人标同一批，算 Cohen's kappa；分歧先讨论再定，不直接取多数。
