[Heading1] 3 首要问题是执行路径没有统一接入
[Heading2] R01 模块实现与实际生效之间存在空档
runtime.Ctx.call 从第 375 行开始，实际依次做工具白名单、guard_tool_args、sim.validate_args、缓存与故障处理、可选 ApprovalGate，再调用 sim.call_tool。当前路径没有调用 tool_contract.authorize 或 security.guard_tool_intent；扫描流水线也没有在这里统一调度。单独测试模块通过，不能证明真实调用已经经过这些检查。
本次在 enforce 与 AGENTLAB_SECURITY_INTENT=1 下，把意图门禁和结构契约替换成恒定 deny，把实际工具替换成无副作用的标记返回。Ctx.call 仍调用工具一次并返回标记；两项门禁调用数均为 0。这证明的是接入缺口，不表示已有参数规则全部失效。
[Heading2] 整改位置与执行顺序
在 runtime.py 建立唯一 ToolExecutor 或等效入口。按可信身份与任务目标取策略，校验严格参数模型和资源授权，执行必要的语义意图检查，再核对审批和幂等键，最后执行工具。工具返回先经过职责与内容检查，再进入模型上下文。任何真实工具适配器都通过该入口。
为每次调用生成稳定 call_id，记录启用策略、已执行检查器、decision、工具是否真正执行、是否产生副作用。deny 和待复核应由执行层明确停止动作，不能仅把 findings 写入日志。audit 保留旁路观测语义，报告中与 enforce 分开。
[Heading2] 实验配置与真实工具配置
当前 Ctx 的 approval_gate 默认为 None，是为了保留历史实验。保留这一兼容模式，同时新增明确的受控执行配置：出现写副作用工具却没有审批后端时拒绝启动；必要检查器未注册、身份未知、可信目标缺失时按该配置转复核或拒绝。启动时打印或导出生效配置，不能仅依据环境变量名推断防护开启。
[Heading2] 验收必须走完整调用链
至少覆盖：结构授权拒绝、意图拒绝、判定服务不可用、首次写无审批、批准后参数改变、批准后恢复和正常调用。每项都断言真实执行函数调用次数；拒绝时应为 0，正常放行时应为 1。原有历史实验继续使用显式兼容配置，分别报告结果。
[Heading1] 4 工具契约与审批摘要的输入问题
[Heading2] R02 同一语义的多个字段没有统一解释
tool_contract._find 在第 89 行开始，只返回第一个非空别名。AMOUNT_KEYS 顺序为 amount、total、max_amount。本次输入 amount=1、total=20000、order_id=A1001，并提供任意非空审批字符串，enforce 授权结果为 allow；金额检查只看了 amount。若下游业务读取 total，就会发生校验值与执行值不一致。该反例在契约模块复现，当前 runtime 尚未调用该模块。
审批字段目前只检查 approval_request_id 是否非空，没有核验票据状态。它可以作为前置格式条件，但不能作为写操作已获批准的证据。URL、路径、资源等字段也使用首个别名策略，应逐类检查冲突；资源 ID 格式正确还不能证明该身份拥有资源。
[Heading2] 整改方式
每种工具定义一个严格参数模型：必填字段明确，未知字段默认拒绝。确需兼容旧别名时，在入口归一化一次；多个别名值冲突立即拒绝。授权、审批摘要和实际执行必须消费同一个已验证对象，禁止下游再次选择另一套字段。金额用业务规定的小数或最小货币单位，资源校验另加所有权与操作范围。
审批请求 ID 只在统一执行层交给 ApprovalGate 验真；调用方不能靠字符串自行声明批准。将未知工具、缺失金额、冲突 URL、未知参数、金额非有限数和资源越权作为反例，确保合法业务仍能完成。
[Heading2] R03 全局规范化可能把不同参数变成同一摘要
approval.canonical 第 78 行起把所有数字转换成 float 并四舍五入到六位，把所有字符串 strip。本次确认：9007199254740992 与 9007199254740993 摘要相同；1.0000001 与 1.0000002 相同；file 与首尾带空格的字符串也相同。当前订单金额未必使用这些值，但通用审批摘要已存在等价关系过宽的问题。
改为按字段语义规范化。整数保持整数精度；金额按工具约定定标；路径、查询或正文只有在执行器也采用相同语义时才归一化。将规范化算法版本与工具 schema 版本写入审批，摘要对象直接作为执行输入。不能只修改哈希算法而继续使用有损规范化。
[Heading1] 5 审批版本绑定与并发消费需要补强
[Heading2] R04 候选版本被存储但没有参与消费校验
approval_requests 已保存 candidate_version 与 idempotency_key；require 查询已批准记录时主要匹配 run_id、tool、args_digest 与状态，然后校验策略摘要、过期与消费状态。当前没有比对本次候选版本和幂等键。consume 入口也没有候选版本参数。
本次先为 v1 与 key-v1 创建审批并批准，再以同一参数请求 v2 与 key-v2，结果仍为 consumed，并返回原来的 key-v1。审批并未绑定到调用方期望的新版候选。是否造成业务错误取决于版本变动内容，但旧批准不应自动覆盖新的执行上下文。
把 candidate_version、tool_schema_version、完整 policy_digest、任务或租户作用域及幂等键纳入不可变审批上下文。消费时显式传入并逐项比对；缺失必需值也拒绝。版本改变需要重新审批，或提供可审计的等价迁移规则，不能静默继承。
[Heading2] R05 一次性消费不是原子状态迁移
require 和 consume 先读取 approved 记录，再在另一段连接操作中执行 UPDATE；更新条件仅为 id，没有同时要求状态仍为 approved 且 consumed_at 为空。本次用屏障使两个线程都先读到已批准状态，两次 consume 均返回 consumed。测试只改审批临时库，没有执行结算或任何外部动作。
在同一事务中进行必要校验与条件更新，或使用带状态、过期和版本条件的 UPDATE 并核对 rowcount=1。SQLite 可用短事务 BEGIN IMMEDIATE 等方式控制竞争；失败的一方必须返回已消费或状态冲突。approve、reject、expire 等迁移也应采用条件状态转换，避免并发覆盖。
[Heading2] 审批与幂等需要分别保证
SettlementLedger 已有唯一幂等键，可以阻止部分重复落账；它不能替代通用审批的一次性保证。修复后同时测试两层：两个竞争消费者只允许一个成功，同一业务键重复提交只保留一笔。同键不同内容必须报冲突。跨系统提交再增加结果查询与恢复协议，避免把审批已消费直接当作业务已成功。
针对当前模块应增加版本变化、幂等键变化、并发消费、并发批准与拒绝、审批过期边界和提交后响应丢失测试。沿用现有暂停与检查点能力，不重写状态机。
[Heading1] 6 语义与职责检测需要明确执行语义
[Heading2] R06 意图判定只看到参数前四百字符
security.guard_tool_intent 第 806 行起已实现 allow、deny 与 review；模型异常也会给出复核建议。第 829 行将序列化参数截断为 body[:400] 再交给 judge_alignment。长参数尾部的实际动作字段可能完全不可见。本次在尾部放置无害标记，捕获判定器输入，确认标记未被传入。
整改时按 schema 选择与授权有关的字段，保留工具名、动作、目标资源、金额、外部接收方和任务目标等关键内容。超预算时显式记录未覆盖字段并转复核，或者分块后保守合并结果。完整参数摘要用于绑定执行，不可声称摘要本身能让模型理解被截断内容。
[Heading2] 模型状态和内容状态分别处理
统一输出 allow、deny、review、error 或等效状态，区分超时、连接失败、格式错误与内容不合规。执行层为每种状态定义行为；受控写操作的 review 或 error 不得静默当成 allow。判定器不代替结构授权，模型也不能从外部文本中修改自己的权限或可信用户目标。
设置每任务模型调用次数、token 与超时预算，并对跨步骤缓存绑定模型版本、策略版本、目标与参数。预算耗尽应有明确终态。CPU 规则也应测时，不能把没有额外模型调用描述为零延迟。
[Heading2] 工具职责规则的适用边界
action_scope 检查只读工具返回中要求助手执行动作的句子，是有价值的低成本补充。它不等同于“所有工具返回出现动词都是攻击”：产品说明、操作手册和对用户的合法指引可能包含祈使句。否定式、引用、转述、语言和主语都可能影响判断。
当前部分结果是 warn 或 info，扫描流水线可以将其映射到复核，但 runtime 未统一使用该流水线。整改需按工具与数据角色定义可信度：允许作为资料展示，禁止自动升级为工具指令；高风险后续动作仍走结构授权和审批。增加中英正常手册、引用中的命令、同句否定加后续请求、未知工具和长文本回归。

[Heading2] R07 召回和误报使用了不同统计单位
eval_action_scope.evaluate 对同一句攻击话术下的多个工具上下文取 any-hit，只要一个上下文命中，该话术就计为 TP；正常对照则逐 case 计 FP。80.6% 因此是话术分组的任一命中率，不是逐工具上下文召回。它不能直接与另一份逐 case 统计的 5.0% 语义召回比较并宣布提升十六倍。
同时输出逐 case 混淆矩阵、逐话术宏平均、任一变体命中率和最差工具家族表现；比较不同检测器时使用相同样本、入口、单位与分母。保留当前数字作为历史结果，修改生成器并生成新协议版本，避免只改 Markdown 文案。
[Heading2] R08 中文模板样本需要完成形状校验
tests/test_chinese_corpus.py 的 test_text_is_non_empty_chinese 在 zh_jb/B2_ctf_slot 上失败，当前取出的文本未包含中文。应回查 import_chinese_corpus.py 的字段选择及模板槽位：若它是尚未实例化的模板，应先实例化或改成明确的非中文子集；若导入字段错误则修导入。不能为了全绿直接删除断言或随意删掉漏检样本。
31 条材料来自红队模板集合，现有报告已说明不代表线上分布。本次未重新运行模型验证这些模板的攻击效果。中文直接越狱、工具返回中的中文间接注入和权限越界是不同任务，职责规则在英文数据上的表现不能作为中文防护已解决的证据。
[Heading2] 测试集复用与报告措辞
v2 报告披露因修否定式误报而重复运行测试集，这是有用记录；“只验一次”仍出现在表头与 rule_note，需同步修正。两次数字相同只说明这些样本结果未变。将该集固定为回归集，下一轮另设未接触的任务家族测试集，并把“零延迟”改为“零额外模型调用，CPU 开销待测”。

[Heading2] 先固定攻击入口和可观察后果

[Heading2] 拆分和标注
按攻击来源、模板家族、工具家族和正常任务类型分组，避免同一话术换工具或同源模板跨开发与验收。冻结测试清单、原始内容哈希和适用标签。模型裁判或规则生成的标签单独标明；有条件时做独立人工复核，记录分歧与裁决，不把模型间一致性当成人工一致性。
建议先用小规模受控工程冒烟验证链路，再开展具有足够独立案例的评估。零次观察到违规不等于风险为零，报告样本数和区间；相关模板按家族统计或重采样，避免把大量改写误作独立样本。所有漏检保留代号与失效原因，不用更换分母掩盖。
[Heading2] 成本也作为结果
报告规则与模型分层的 p50、p95 延迟、额外模型调用数、token、待复核率和正常业务误阻断率。性能测量注明硬件、模型服务位置、预热和并发。已有历史 Qwen 结果仍可引用为历史产物，但本轮没有重跑，不能拿旧耗时解释当前新增门禁的成本。
[Heading1] 9 冻结配置与服务边界
[Heading2] R09 基线指纹漏掉主要安全模块
baseline.py 的 CODE_FILES 仍是 11 个显式文件。本次核对确认 security.py、approval.py、tool_contract.py、semantic_guard.py、action_scope.py、scan_pipeline.py 和 code_guard.py 均不在其中。它们改动时，当前代码文件清单可能不反映防护逻辑变化。已有技能库内容指纹仍有价值，应扩展而不是推倒重做。
纳入当前生效安全模块、策略与工具 schema、扫描器配置、提示词、阈值、模型版本、安全模式及全部有效开关。工作区有修改时记录源文件内容哈希与 dirty 状态，不能只写 HEAD。数据清单和拆分也须有指纹；缺文件或无法读取不能静默省略。旧 manifest 保留协议版本，新规则使用新版本。
[Heading2] 验证指纹确实随风险相关变化而变化
临时复制一份源文件或配置，修改一个安全阈值、审批版本或模型提示词，验证新 manifest 不同且混跑检查拒绝合并。无需改动原项目即可完成这种验证。避免仅写一个断言“清单包含七个名称”，应证明真实行为依赖的配置变化能被捕获。
[Heading2] 本地服务与部署条件
当前 API 以本机回环服务为主要边界，适合个人实验。若后续允许其他人访问，再明确身份认证、请求体大小与模型预算、任务并发隔离、审批权限和日志脱敏。不能把只有回环监听的服务直接描述成已经存在公网漏洞，也不能在开放监听后沿用单用户假设。
审查共享进程状态对并发实验的影响，运行参数与强制技能应按请求隔离。将网络调用、任务取消和超时传递到下游。代码安全扫描或 AST 检查不等同于执行沙箱；未来开放生成代码或 shell 工具前，单独定义目录、网络、进程资源与凭据边界。
[Heading2] 文档同步
维护一张当前能力表：入口、默认配置、开启条件、真实执行点、测试和能力边界。历史报告保留日期，不回写旧数字；生成器与新报告一起改。docs/security.md、plain-intro 及实验介绍中的最新描述以本轮运行证据为准。

[Heading2] 每次提交的共同要求
保留现有未提交工作，不重构无关模块。先写能重现该问题的行为测试，再做最小修复；完成相应测试后运行必要的集成回归。报告功能是否实际开启、拒绝时工具是否执行、对正常任务有无影响。涉及历史模式时显式保留兼容配置与协议版本。
[Heading2] 暂缓事项
先完成 P0，再考虑扩大检测器、引入大模型权重、微调或更换技术栈。当前主要问题是确定性执行控制与评测口径；增加更大的模型无法修复审批竞态、别名冲突或未调用的门禁。NeMo 的模型检查器通过可选适配器逐步接入，先用替身验证配置与调用，再决定真实模型成本。

[Heading1] 12 验收清单与完成标准
范围
必须看到的行为证据
执行接入
从实际任务入口触发契约 deny 与意图 deny，真实工具调用数都为 0
配置校验
真实写工具缺审批后端、未知必要检查器或无效配置时拒绝启动
参数一致
冲突别名、未知字段、缺必填值被拒绝；授权与执行使用相同对象
摘要语义
不同大整数不碰撞；不同精度字段按 schema 解释；执行器语义一致
审批上下文
候选版本、策略、schema、幂等键改变时，旧审批不能被消费
原子消费
受控并发重复测试中，仅一个消费者成功；状态迁移冲突可定位
幂等恢复
响应丢失与进程重启后无重复落账；同键不同内容明确冲突
语义覆盖
尾部关键字段不静默丢失；超时、无效输出与超预算不等同于放行
工具返回
职责信号接入上下文策略；正常手册与未知工具有明确处理
数据质量
中文案例字段和槽位可解释；失败测试修复；来源许可与内容指纹齐全
评测口径
逐 case 与逐话术结果分别输出；测试集版本与重复使用如实披露
可复现性
安全代码或有效配置变化引起 manifest 变化；不同基线拒绝混算
[Heading2] 工程完成与研究结论分别验收
P0 行为测试通过、正常任务可完成、全量回归无未解释失败，才可称本轮工程整改完成。要宣称防护比现有方法更好，还需要相同数据和预算下的独立对照，报告攻击目标达成、正常业务损失及成本。没有这些结果时，可以准确表述为“完成防护接入与一致性加固”。
本报告是审查与实施方案；项目代码尚未按建议修改。所列缺陷有代码或受控反例支持，部署扩展项属于未来开放使用前的建议，不代表当前已发生外部攻击。
