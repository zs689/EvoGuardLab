# AI 保障系统：可靠 + 防护 + 可运行

这个项目要回答的不是「模型准不准」，而是：

> **这个 Agent 现在能不能放心让它自己跑？哪一维没测？哪一维测了但有问题？**

所以判定分三个维度，各自独立给结论，**不合成 0–100 分**。
把「3 条 warn + 1 个测不了的维度」压成一个分数，分数看着专业，
但没人知道 82 分能不能上线；而且一旦有分数，所有人都会开始优化分数。

## 三个维度

| 维度 | 回答什么问题 | 用什么测 | 现在能测到什么程度 |
|---|---|---|---|
| **可靠** reliability | 结论对不对、流程有没有乱、资源有没有失控 | 轨迹规则 25 条（answer/tool/flow/resource/structure） | 能测「结论有没有证据支撑」；**测不了业务上该不该这么做** |
| **防护** security | 有没有被注入、越权、外带、泄凭据、执行危险命令、输出 XSS | `security` 组 6 条规则 + 运行时 6 个执行点 | 特征匹配可绕过；白名单拒绝与写操作审批在 `enforce` 下真执行；沙箱仍没有 |
| **可运行** operability | 模型/工具健康吗、有没有预算超限、报错后还在出答案吗 | 轨迹里的步骤状态、耗时、token、错误类型 | 只看轨迹；**不是线上 SLA、不含并发与限流** |

判定取值：`通过 / 有风险 / 不通过 / 覆盖有限 / 无法判定`。
总判定取三个维度里最差的那个 —— 只要有一维「无法判定」，整体就不写「通过」。

## 怎么跑

```bash
cd ai-service

# 直接把一个运行库当输入（按文件头识别 SQLite，不看后缀）
python -m evoguard_inspect.cli \
  --trace ../experiments/p0_09_20261109/audit_smoke/evolution.db \
  --assurance --out ../experiments/assurance

# 也可以喂标准格式
python -m evoguard_inspect.cli --trace otel.json --assurance
python -m evoguard_inspect.cli --trace langsmith.json --assurance

# 只对某个 Agent 的轨迹做，并收紧白名单（否则越权那条测不了）
python -m evoguard_inspect.cli --trace t.json --config inspect.json --assurance
```

退出码：`0` 通过/有风险；`3` 不通过；`2` 输入解析失败（配 `--strict-input` 时部分失败也算）。
产物：`assurance.md`（给人看）+ `assurance.json`（给 CI / 看板）。

## 报告长什么样

`experiments/p0_09_20261109/assurance/assurance.md` 是 3205 条轨迹的历史产物（冻结原件，
其中「审批与沙箱只有声明」是旧描述）；当前版本报告在 `experiments/assurance_v2/`：

- 总判定 + 三维判定表（每行带一句依据，不是只有分数）
- 每维固定写两行：**测了什么** / **没测什么**
- 覆盖与缺口：规则可执行率、因输入不足跳过的规则名、轨迹里有哪些输入
- 数据画像：多少条带注入故障。**不写这一句，失败率会被当成线上失败率读。**

## 一个刻意不做的事

不输出「保障分数」。也不把「零命中」写成「通过」：
有规则因为缺 token 用量、缺时间戳、没配 `allowed_tools` 而没跑时，
判定是 **覆盖有限**，报告里会列出具体是哪几条规则没跑。

这条规则来自实际教训：一张写着 0 的体检单，如果一半项目没做，
它比不做更有欺骗性。

## 与「两套模块」的区别

在此之前，可靠性和防护是两个平行模块：轨迹规则查一摊、安全规则查一摊，
各自出报告。问题在于没有一处的结论是「所以能不能用」。

现在 `assurance.py` 只做三件事：分组、算健康指标、给三维判定。
它不新增检测能力，也不掩盖任何一维的缺口 —— 缺什么就写在「没测什么」里。

## 已知缺口（按重要性）

1. **标注集只是回归护栏，不是真实准确率**：现有 37 条构造集（`trace-label-v2`，
   标签来自执行时的注入状态），两档口径 error 级 recall 0.412 / precision 1.000、
   warn 级误报 2/20。样本全部来自本仓库、标注者即规则作者，没有外部真实轨迹与
   独立标注；不能写成「准确率 41%」或「误报率 0」。详见 `docs/labeling-protocol.md`。
   另外 `eval_labeled.py` 把轨迹实际用到的工具填入 `allowed_tools`，所以它**不能**
   用来判断越权（权限专项需从事先冻结的策略取白名单，见推进计划 §7 Q02）。
2. **防护是特征匹配**：可绕过。最小权限与写操作审批已经能在 `enforce` 下真执行
   （代价实测：单故障 D -26.5pp、复合链 -40pp，见 `mode_compare.json`）；
   **沙箱仍然没有**，真要跑 shell 工具时没有隔离层。
3. **可运行只看轨迹**：没有 SLA、没有并发、没有成本曲线；真实部署的可用性这一层没做。
4. **多 Agent 只到库级**：`check_peer` 有了，但运行时没有多 Agent 链路可验。
5. **判定阈值是经验值**：模型报错率 >20% 判不通过、10% 判风险 —— 这两个数是拍的，
   没有线上数据校准，改之前先想清楚依据。
