| reflect_replan（反思重规划） | 23 | **65.22%** | 4.22 | 0 |

**ΔSuccess = +4.35 pp，ΔAvgSteps = -0.39**（同模型配对，剥离模型强弱变量）。

> ⚠️ **本节 +4.35pp 的结论已被 DOCKER-OPT-01 更正为不成立**（见下文）。
> 保留原文是为了留下完整的判断轨迹：当初据此认为「架构有正增益」，
> 后来定位到环境摩擦，修复后 Δ 翻成 −4.35。**当前结论：n=23 下
> reflect 相对 linear 无可证实的增益。**

当时的观察：
- 基线 60.87% 说明题目有真实难度（不是全过/全不过的玩具集）；
- 注入题（3 道）在两臂下 `attack_executed=0`，安全门禁未被架构升级削弱。

## 容器隔离复测（Docker 可用后，2026-11-20 晚）

本机 Docker Desktop 安装并启动后（Engine 29.7.2 / 镜像 `python:3.11-alpine`），
用 `--use-docker` 在**真容器**（非 root、只读挂载 `/work`、256m 内存上限）
重跑同一套 23 题 × 2 臂：

| linear | 23 | 47.83% | 5.78 | 0 | docker |
| reflect_replan | 23 | 52.17% | 7.52 | 0 | docker |

**ΔSuccess = +4.34 pp，ΔAvgSteps = +1.74**。

### 两次后端的对照（初版观察，后被 DOCKER-OPT-01 更正）

| 后端 | linear | reflect | ΔSuccess |
|---|---|---|---|
| local-subprocess | 60.87% | 65.22% | **+4.35 pp** |
| docker（容器隔离，未修摩擦） | 47.83% | 52.17% | **+4.34 pp** |

> ⚠️ **这段初版解读已被推翻，请看下文「DOCKER-OPT-01」一节。**
> 当时以为「Δ 在两后端一致 ⇒ 不是环境假象」，但后续定位到容器环境
> 摩擦（工作目录没挂载）并修复后，Δ 翻成 −4.35。两次一致的真正原因是
> **同一个偏差源**，不是架构稳健。

同时必须注意两点差异，不做粉饰：
1. **绝对通过率下降 13pp**（60.87%→47.83%）：容器更严格（只读工作区、
   资源受限、无宿主缓存），题目在容器里更难。绝对分数应以容器版为准。
2. **步数方向相反**（子进程 −0.39，容器 +1.74）：reflect 在容器里为了
   通过更严格的测试多花了步数。即「用更多步换成功率」，不是纯效率提升。

## DOCKER-OPT-01：修掉环境摩擦后的复测（并更正上面的结论）

**根因**（逐题 diff + 读代码定位）：`DockerCodeSandbox.run()` 只挂载了
**单个脚本文件**，没有挂载 Agent 实际改动的工作目录。于是 Agent 用
`fs.write` 改完文件后，在容器里 `import` 不到它 —— 只能反复重写同一段
代码，最终被 `loop_guard` 熔断。失败题的 `stopped_by` 全是
`loop_detected` / `max_steps_exhausted`，不是环境报错，正是这个症状。

**修复**（隔离边界一条没动）：`run()` 新增 `work_dir`，以 `:ro` 只读挂
到 `/work`，并加 `PYTHONPATH=/work`、`PYTHONDONTWRITEBYTECODE=1`
（只读目录里写 `__pycache__` 会抛 PermissionError 掩盖真实错误）、
`HOME=/tmp`。仍然 `--network=none --read-only --user 65534:65534
--cap-drop=ALL --pids-limit=64`，并实测容器内写 `/work` 失败、宿主机无痕迹。

| 后端 | linear | reflect | ΔSuccess | linear 步数 |
|---|---|---|---|---|
| 子进程（早期） | 60.87% | 65.22% | +4.35 | 4.61 |
| 容器·修复前 | 47.83% | 52.17% | +4.34 | 5.78 |
| **容器·修复后** | **65.22%** | **60.87%** | **−4.35** | **4.87** |

两件事同时发生，必须一起看：

1. **环境摩擦确实被消除了**：容器通过率 47.83% → **65.22%**（+17.4pp），
   平均步数 5.78 → 4.87。容器现在甚至不低于子进程。
2. **「反思重规划有正增益」的结论被推翻**：修复后 ΔSuccess 从 +4.34
   翻成 **−4.35**（23 题里差 1 题）。也就是说，之前两次「+4.35 / +4.34
   高度一致」并不是架构稳健的证据 —— **它来自同一个偏差源：环境摩擦**。
   reflect 臂因为多走几步、多试几次，更容易在摩擦中碰巧撞对，从而虚高。

**更正**：`reflect_replan` 相对 `linear` 的增益在 n=23 下不成立（±1 题
即 ±4.35pp，属噪声）。要判定架构增益，必须先把环境摩擦清零（本次已做），
再用 n≥60 的配对基准 + 统计检验。这与 EVO-BENCH-01 的教训一致。

## 诚实边界（必须一起读）

1. 三条 `backend` 结果全部保留：`ab_result.json`（子进程）、
   `ab_result_docker.json`（容器修复前）、`ab_result_docker_after.json`
   （容器修复后），各自标注，**不混用**。
2. **题数 23 = 题库当前实际规模**（含注入题），以 `n` 字段为准。
3. 通过率由隐藏测试在真实文件系统上判分（读回 Agent 实际写入的文件），
   评测脚本不含修复答案，非自证。
4. 单次运行有模型随机性；±1 题 = ±4.35pp，任何小于 2 题的差异都不能当结论。

## 结论（已与上方更正对齐）

**当前有效结论：在消除容器环境摩擦后，Reflect-Replan 相对 linear 没有
可测的正增益。** 容器修复后复测为 linear 65.22% vs reflect 60.87%
（Δ = −4.35pp，n=23，±1 题即 ±4.35pp，属统计噪声范围内）。

早期记录的 +4.35pp / +4.34pp「高度一致」来自同一个偏差源（环境摩擦）：
reflect 臂多走几步，更容易在摩擦中碰巧撞对。那段结论**已被推翻**，
但原始数字保留在 `ab_result.json` / `ab_result_docker.json` 里以便追溯，
不混用、不删档（完整更正脉络见上方「两件事同时发生」与「更正」段）。

仍需：
- 用 n≥60 的配对基准 + McNemar 检验判定架构增益（已由 EVO-BENCH-01
  的 env-bench 承接，见 experiments/skill_ab_real/）；
- 换第二个模型交叉验证模型无关性；
- 反思改为**按需触发**（连续同错或近 loop_guard），不再无条件插提示
  （见 MOD-AGENT-01 的 should_reflect）。
