## 0. 一句话

让 Qwen3-4B 自己学一遍（探索 39 例 → 38 个候选 → 严格验证只放行 6 个），
四组对照第一次出现了**方向相反的两组差距**：

- 复合故障：D 100% ，C **0%**

也就是说治理不是「处处更好」，而是**在需要多步的时候，不让没验证过的技能把有效的链挤掉**。

## 3. 复合故障：C 为什么是 0%

C（放宽库）有 38 条技能，D（严格库）只有 6 条 —— 其中 5 条是两步链，作用域 `multi`。

- **D**：`kb/retrieval_failure` 这类键上只有一条技能，就是链 → 第一轮直接用链 → 两个坏点一次拔掉 → 100%。
- **C**：同一个键上有单步技能（`fallback_tool`、`retry`…）也有链。第一轮恢复优先**单步**技能
  （作用域 single 优先），它只能拔掉第一个坏点；而运行时**一轮恢复只走一条链**，
  链长 1 就结束了 —— 第二个坏点没机会被处理 → 0%。

所以 C 的 0% 不是"模型不行"，是**它的库里垃圾太多，把有用的链挤到了永远轮不到的位置**。
这恰好就是"不严格验证"的真实代价，而且是在四组对照里第一次显形。

## 4. 单故障：D 为什么反而低 2.9pp

D 一共 6 条失败，全部是 `planner/incorrect_planning`，恢复链是 `human_takeover`。

成因在训练里：这条候选技能在验证集上 `before=0% / after=0%` —— 真实模型用 `cross_verify`
也救不回来，所以严格验证拒了它。而规则表故意没有 `incorrect_planning` 的策略（留出学习空间），
于是这些用例只能转人工。

**这是能力缺口，不是治理出错**。同一批里 `planner/tool_hallucination` 也是
`before=0/after=0` 被拒，但规则表有对应策略，所以没掉分。
mock 库里这条 `incorrect_planning → cross_verify` 是存在的 —— 说明**mock 的成功有虚高**。

这 6 条里有 3 条恰好伴随模型报错（`E_LLM_HTTP`）。我一度把它们判成「不可评」，
重算后 D 变成 98.5%。**这是错的，已经撤回**，下一节写清楚为什么。

## 4b. 我在这条上改错过一次（留档）

时间线，同一天内：

| 版本 | 规则 | D 的结果 | 问题 |
|---|---|---|---|
| v1 | 失败就计失败 | 97.1% | 没区分「评测条件受损」 |
| v2 | 有 `E_LLM_*` → 不可评 | **98.5%** | **把注定失败的案例洗掉了** |
| v3（现行） | 只有**框架异常** → 不可评 | 97.1% | —— |

v2 错在哪：我去查了那 3 条 run 的完整轨迹。以 `planner/refund/incorrect_planning` 为例——

```
L2 tool  task.make_plan  ok    {"steps": ["财务退款","生成退货单","确认退货原因","核对订单"]}   ← 倒序
L3 context build_context ok    同上
L5 model answer          error E_LLM_HTTP  {"parsed": null, "text": ""}
answer = 倒序计划（工具兜底）   expect = 正序计划
```

`incorrect_planning` 这个故障的作用就是让工具返回倒序计划，而规则表没有对应策略
（`human_takeover`）。也就是说 **不管模型答不答，这条都注定失败**。
模型那步报错只是表象，不是失败原因。把它判成不可评，等于用「服务抖了一下」洗白真实失败。

更危险的是：如果这条规则留着，以后 A 模式（无恢复，本来就该 0%）的失败也能被同样理由洗掉。

现行规则（v3）：

- `success=False` 且 **框架异常**（`error` 非空，run 根本没跑完）→ `unjudgeable`，出分母
- `success=False` 但 run 跑完了、有答案 → `failed`，**必须计分**
- 失败里有多少条伴随 `E_LLM_*`：单独记 `failures_with_llm_error`（D 是 3 条），供审计，不动分母
- `bad_model_output`（模型吐出非 JSON）一律计分

本轮 450 条失败里**没有一条是框架异常**，所以可评率 100%。也就是说：
这批数据本来就没有被污染，`unjudgeable` 机制这次没有派上用场 —— 但它是以防万一的闸门，
真正需要它的场景是「整个批次的服务全挂」（下一节）。

## 4c. 批次级：全批次失效不能输出 0%

单个 run 报错还能算失败，但如果一个批次**所有调用都失败**，那不是质量数据，是事故。
本轮 grammar 对照就撞上过一次（Ollama 挂了）：6 次调用全是 `E_LLM_UNREACHABLE`，
旧代码照样算成「严格 JSON 成功率 0%」——等于宣称模型格式合规率 0%。

现在 `grammar_control` 有 `valid` 字段：可评次数为 0 时**不输出任何比率**，
报告直接写「本批次无效，不能据此得出 0%」。

## 5. 这轮修掉的两个「静默 bug」（都属于让结论作废的那类）

1. **探索时传错了技能键**：把复合故障的 `"missing_field+silent_corruption"` 当成强制技能的
   `fault_type` 传进去，而运行时授权要求 `fault_type == root_cause`（实际是 `"missing_field"`），
   所有候选被静默丢弃 → 第一次训练 33 个候选里**链数是 0**，表现成"复合故障学不会"。
2. **复合样本切分按列表位置**：`comp[:half]` 是按模式排的，切完 order 的模式全在训练侧、
   验证侧一条都没有 → order 的链全部 `NO_TARGET` 被拒。改成"按模式分组后按任务切"。
   现在 `NO_TARGET` 会打日志，不再静默。

再加上 run1 那个排序 bug（`ORDER BY version DESC` 并列时按扫描顺序取行，取到最早插入那条，
复合 C 停在 40%），这一个月里同一类问题出现了三次：**结果取决于数据库顺序 / 静默跳过**。
现在的对策是：所有排序给足兜底、所有跳过必须打印、每个修复都配一条能区分新旧行为的回归测试
（`TestSkillLookupDeterminism`、`test_scope_separates_multi_from_single`）。

## 6. 技能作用域：为什么非加不可

技能原本只按 `(agent, fault_type)` 建索引，而复合故障的根因是它链里的**第一个**故障。
于是复合学到的两步链会挂到单故障的键上 —— 实测把 `kb/retrieval_failure`
单故障的 6 个用例全打挂了（本该用一步 `fallback_tool`，却被套了一条链）。

现在技能带 `scope`：`single`（单坏点学来的）/ `multi`（多坏点学来的）。
恢复第 1 轮优先 single，第 2 轮起优先 multi；只是排序偏好、不硬过滤
（多故障场景下一条单步策略仍可能是正确的第二步）。

## 7. grammar 对照：`format_violation` 不是假想故障

| | 有 `format=json` | 无 grammar 约束 |
|---|---|---|
| 严格 JSON 成功率 | 100%（主实验全部） | **0/6** |
| 平均延迟 | 约 700 ms | **10505 ms** |
| 形态 | JSON | 中文推理散文（"嗯，用户让我只输出 JSON……"） |

真实部署里，Qwen3 4B 不加约束就是**必然**格式违规。
但主实验里的 `format_violation` 是注入的，不能拿它当模型真实犯错率。

## 8. 这轮仍然没证明什么

1. **模型能力**：936 次调用 0 次错答。任务是抽取式的，grammar 又把格式错误清零，
   这份数据集压不出模型的推理错误。
2. **统计效力**：单次运行，无多 seed；验证集每格只有 1 条用例（1 个 before/after 就决定晋升与否）。
3. **真实工具链**：仍是内存模拟，没有真文件读写 / HTTP 超时 / DB 错误。
4. **负迁移只在同键内被挡住了**：guard 只覆盖「同 agent 不同故障」，
   「同故障不同类型（单/复合）」是靠 scope 挡的，没有单独的量化指标。

## 9. 下一步（按能改变结论的力度）

1. **提任务难度**：多步计算 / 跨文档推理，让模型真的会答错 —— 否则"Agent 可靠性"永远测不到模型那一层。
2. **扩大验证集**：每格至少 3 条，现在 1 条样本的验证等于抛硬币，容易误杀（§4 就是例子）。
3. **接真实工具**：把 `sim` 换成真文件 / 真 HTTP，验证故障在真实链路上还能不能被抓住。

## 10. 难度组：第一次真正测到模型

前面 9 节的所有数字都建立在一个前提上：**任务是抽取式的，模型只要搬运**。
936 次调用 0 次答错就是这个前提的直接证据 —— 测的全是恢复机制。

所以另开一组 `--suite hard`（36 例 × 4 模式 = 144 run，单独落盘 `hard/`）。
这一节记录它改了三版才成立的过程，因为中间两次都测错了东西。

### 10.1 三版演进

| 版本 | 设计 | 基线 | 问题 |
|---|---|---|---|
| v1 | 工具只给原料，**模型自己算多步** | 33.3% | 三题错法各异，但没有区分错因 |
| v2 | v1 + prompt 明确"不得复制小计、两步都要做" | 33.3% | **无效**，H3001 从"算错 3820"退化成"抄小计 4020" |
| v3（现行） | **算术交给工具，规则顺序交给模型** | **83.3%** | —— |

v1 的三道错题（现在看起来很有价值，因为它把病因分开了）：

| 订单 | 小计 | 真值 | 模型答 | 病因 |
|---|---|---|---|---|
| H3002 | 2855 | 2389.5 | 2855 | 等于小计 → **压根没算**（指令理解） |
| H3001 | 4020 | 3724 | 3820 | 算了但**顺序反**（规则理解） |
| H3003 | 750 | 750 | 650 | 没到门槛却减了 → **条件判断** |

v2 证明了一件事：加约束教不动 4B 做多步算术。所以 v3 换分工 ——
这不是降难度，是把考点从「会算数」挪到「会编排规则」。
真实业务里没人让 LLM 自己算账，Agent 的活是决定顺序、调对工具。

|---|---|
| 纯能力基线（无故障，24 run） | **83.3%**（6 题对 5 题） |
| A 无恢复 | 22.2% |

按故障看 D（这才是可用的诊断表）：

| 故障 | D 成功率 | 怎么读 |
|---|---|---|
| tool_exception | 3/3 = 100% | 瞬时故障，重试就过 |
| tool_timeout | 5/6 = 83.3% | 同上 |

两个 0% 是**真结论**，不是机制坏了：这两类故障的共同点是
「Agent 手里只有一份被污染 / 过期的数据」—— 任何恢复策略都需要"另一份证据"才能比对，
而这组任务里 Agent 拿不到。这和已知限制里「`silent_corruption` 对 KB 不成立」是同一条边界。

### 10.3 这组不测 `format_violation`（一个语义问题）

第一版把这组也放进了 `format_violation`，结果 0/6。查轨迹发现不是机制坏了：

```
第7步 model answer  mismatch  format_violation  {"parsed": null, "text": "好的，我来回答：{\"order\": []}"}
第14步 model answer ok                          {"parsed": {"order": []}}     ← reformat 修出来了，但是空的
```

这个故障的注入方式是「拿 fallback 答案包一层散文」。而这一组模型要自己作决策，
Agent 手里没有正确内容，fallback 只能是空结构 → `reformat` 修出来仍是空 → 必然失败。

**故障语义和任务语义不匹配**，测下去只会得到一个看着像机制缺陷的假结论。
所以换成语义成立的 `premature_termination`（答案层故障，重放可救），
换完 D 从 55.6% 变成 69.4%。

### 10.4 顺手抓到的判定 bug

`xref` 的 `cited` 原来精确匹配 `"KB-25"`，但模型很自然地返回 `"KB-25 v5"`，
于是**本来做对的两道被判成错**。修法：正则提取 `KB-\d+` 再比。
不修的话这组会得出「模型完全不会跨文档核对」，实际它会对 2/3。
测试：`test_cited_with_version_suffix_counts`。

### 10.5 下一步

- **分档**：现在 6 题、基线 83.3%，带宽还是偏窄（D 69.4% 距基线只差 3 题）。
  按 easy / medium / hard 各 3 题扩，找"会做但会犯错"的区间。
- **扩技能到新 agent**：`calc` / `xref` 在技能库里没有条目，C/D 都退化成规则表，
  所以这组 C = D 打平。要让它们有区分度，得让训练集覆盖这两个 agent。
- **技能加一个维度**：现在只存"恢复策略"，可以再加"这类题的正确解法"

## 11. 把技能扩到 calc/xref：一次有价值的负结果

上一节末尾说「C = D 打平是因为技能库里没有 calc/xref 的条目」。补上了，结论是：**还是打平，但原因变了。**

### 11.1 怎么扩的（避免泄漏）

技能要能覆盖这两个 agent，训练样本就得覆盖它们；但训练样本绝不能是评测题。
所以给难度组加了一组**专用训练任务**：

| 用途 | calc | xref |
|---|---|---|
| 训练（探索 + 验证） | `T4001`、`T4002` | 换货期限、运费规则 |
| 评测（不变） | `H3001`–`H3003` | 退货期限、保修期限、发票时限 |

工具和真值查的是**合并表**（`ALL_HARD_ORDERS` / `ALL_HARD_KB`），
模型和工具分不出哪个是训练题、哪个是考题 —— 只有 `hard_tasks()` 会区分。
测试里钉了两条：训练任务与评测任务不相交、训练任务必须能被工具查到。

> 后面这条是补的：第一次跑训练时工具只查了评测表，`T4001` 报「订单不存在」，
> 于是探索阶段全部失败、静默产出 0 条 calc 技能 —— 表面看是「学不会」，
> 实际是数据层没打通。这种静默失败比报错难查得多。

### 11.2 扩完的结果：41 条 vs 6 条，分数一样

| 库 | 条数 | 其中 calc | 其中 xref |
|---|---|---|---|
| 放宽库（C） | 38 → **41** | 3 | 0 |
| 严格库（D） | 6 → **6** | 0 | 0 |

难度组四组：A 22.2% / B 44.4% / C **69.4%** / D **69.4%** —— 与扩之前完全一致。

### 11.3 为什么没拉开：两条路径，同一个结果

查 C 与 D 在 calc 用例上的实际恢复策略：

| 故障 | C（用经验） | D（严格库查不到 → 规则表） | 结果 |
|---|---|---|---|
| tool_timeout | `replay_checkpoint` | `retry` | 都成功 |
| tool_exception | `replay_checkpoint` | `retry` | 都成功 |
| premature_termination | `replay_checkpoint` | `replay_checkpoint` | 都成功 |
| silent_corruption | `replay_checkpoint` | `human_takeover` | **都失败** |

C 的库里 calc 只有 3 条技能，最新那条是 `replay_checkpoint`；C 只按 agent 匹配，
于是**对所有 calc 故障都套这一条**。而 `replay_checkpoint`（重放）对瞬时故障也有效，
所以它歪打正着，和精心设计的规则表打成平手。

D 那边：这 3 条技能在验证集上 `gain = 0`（规则表已经能处理这些故障），
严格验证全部拒绝 —— 所以 D 库里一条 calc 技能都没有，全靠规则表。

**这就是本质**：当规则表已经覆盖某类故障时，技能库里再怎么加，都只是规则表的复制品，
加多少条都不改变结果。这和 204 例上 C = D = 100% 是同一个机制，只是换了个靶场。

### 11.4 那怎样才能产生区分度

只有一条路：**让技能能表达规则表里没有的东西**。

现在的技能 schema 只有 `strategy`（6 种恢复策略的组合），它能表达的边界就是规则表的上限。
真正有价值的是「这类任务该怎么解」—— 比如 calc 的规则顺序偏好（先满减后折扣）、
xref 的「比版本号而不是比命中位置」。这类知识规则表根本没有，学出来才有增益，
也才可能被严格验证拒绝（当它是错的时候）。

这是下一步该做的事，也是「自进化」这个题目真正的落点：
**技能不能只是恢复策略的别名**。
