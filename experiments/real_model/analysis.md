# 真实模型评测：这些数字怎么读

> 数字出处：`experiments/real_model/metrics.json`（第二轮，定序后）、
> `experiments/real_model/archive_run1/`（第一轮，留档不复用）、
> `experiments/real_model/attribution.md`（C/D 命中归因）。
> 这份文件是**解读**，不是自动生成的报告 —— 自动报告只给数，判断在这里。

## 0. 一句话

机制层面的相对关系在真实模型（Qwen3 4B）下**完全复现**：固定规则 B 仍是 26.5%，
复合故障上"单步策略 0% / 两步链 100%"依然成立。
但这轮评测**不能**用来证明「严格验证」的价值，也**不能**用来证明模型能力 ——
原因在第 3、6 节，都是可复核的数字，不是免责声明。

## 2. 第一轮那个 40% 是怎么来的（这轮最值得记的一课）

技能库里 7 条已晋升技能，**5 条是同一个两步链** `[fallback_tool, cross_verify]`，
2 条是单步 `cross_verify`（`kb/stale_data`、`planner/incorrect_planning`）。
C 模式只按 `task_type` 匹配，所以同一 agent 下一定命中多条并列行
（version 都是 2）。第一轮的查询是 `ORDER BY version DESC LIMIT 1`，
并列时 SQLite 返回**最先扫描到的行**，实测就是最早插入的那条：

| agent | 第一轮 C 命中 | 策略 | 复合故障结果 |
|---|---|---|---|
| order | `missing_field`（链） | `fallback_tool → cross_verify` | 12/12 成功 |
| kb | `stale_data`（单步） | `cross_verify` | 0/12 |
| planner | `incorrect_planning`（单步） | `cross_verify` | 0/6 |

12/30 = **40%**。这不是"经验在真实模型下失效"，而是**取到了哪条技能**。

定序之后（`version → created_at → rowid`）C 取最新那条，三个 agent 全是链，
于是 30/30。修复与回归测试在 `ai-service/evoguard/skills.py` +
`tests/test_core.py::TestSkillLookupDeterminism`（旧实现取 `sk_old`，新实现取 `sk_new`，
测试能区分两者）。

**教训**：一个数字如果取决于数据库的扫描顺序，它就永远不该进结论。
这个 bug 在 `get_recovery()` 里已经踩过一次（毫秒并列 → 取到链中间的失败步 →
把成功经验判成失败），同一个月踩了第二次。

## 3. B 为什么和 mock 一模一样（26.5%）

B = 固定规则，一律 `retry`，不诊断、不查表、不用技能。所以：

- 204 个 run 里 **102 个连模型都没调到**（恢复前就 FAILED）—— 故障是持久的，重试无效。
- 剩下 102 个：54 个一轮就过、78 个重试后仍失败。
- 972 次模型调用里，**模型答错 0 次**（`bad_model_output = 0`）。

结论：B 的成绩由**故障注入机制**决定，不由模型决定。它不是"模型恰好表现一样"，
而是这条路径上模型根本没有发挥空间。把 B 的 26.5% 当成"模型能力指标"是误读。

## 4. 这轮真正证明的一件事：策略链

| 复合故障（30 例，两个持久故障落在不同逻辑步） | 成功率 |
|---|---|
| A 无恢复 | 0.0% |
| B 固定重试（等价单步） | 0.0% |
| 第一轮 C：命中单步技能 | 0.0%（kb/planner 共 18 例全灭） |
| 两步链 `fallback_tool → cross_verify` | 100.0% |
| D 完整闭环 | 100.0% |

这是**物理限制**的实证：诊断每轮只返回一个坏点，单步策略处理完重放，第二个故障才暴露。
mock 下是这个结论，真实模型下还是这个结论 —— 说明链的收益来自机制，不来自调参或模型。

## 5. grammar 对照：`format_violation` 不是假想故障

| | 有 `format=json` | 无 grammar 约束 |
|---|---|---|
| 严格 JSON 成功率 | 100%（主实验全部） | **0/6** |
| 平均延迟 | 640 ms | 10402 ms |
| 形态 | JSON | 中文推理散文（"好的，我现在需要处理用户的这个请求……"） |

真实部署里，Qwen3 4B 不加约束就是**必然**格式违规：思考通道关掉后它会把推理写进正文。
所以 `format_violation` + `reformat` 这一对不是凑数的故障类型。
但反过来，主实验里的 `format_violation` 是**注入**的，不能拿它当"模型真实犯错率"。

## 6. 这轮没证明什么（不要拿它吹）

1. **没证明治理价值**：C = D = 100%。更难看的是 D 的 204 个单故障 run 里，
   只有 **42 个真的命中了技能**，其余 162 个是内置规则表兜底 ——
   四组对照大部分时间在给规则表打分，不是在给"学习"打分。
2. **没证明模型能力**：任务是抽取式的（从上下文里取一个数 / 一句话），
   grammar 约束又把格式错误清零，972 次调用 0 次错答。这份数据集压不出模型的推理错误。
3. **没证明自举**：技能库是从 mock 闭环迁移过来的 7 条，测的是"迁移是否有效"，
   不是"真实模型自己能不能学会"。
4. **没测稳定性**：单次运行，没有多 seed 取均值，模型随机性未量化。

## 7. 下一步（按能改变结论的力度排序）

1. **让 C 走自己的放宽验证流程**，在真实模型下重新训一套技能库。
   现在 C 和 D 共用同一个技能库，C 的"不严格验证"根本没被激活 ——
   这是 C/D 打平的根因，也是四组对照失去区分度的原因。
2. **让技能覆盖全部用例**：现在每个 (agent, 故障) 只有 1 条技能，
   只覆盖测试集里 6 个用例，剩下全靠规则表。技能覆盖不上去，
   对比就永远是规则表的成绩。
3. **把任务难度提上去**：多步计算、需要跨文档推理，让模型真的会答错，
   否则"Agent 可靠性"永远测不到模型那一层。
